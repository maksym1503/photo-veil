# Privacy, Terms and support publication plan

This is a release-preparation guide, not legal advice and not authorization to publish or deploy. Existing drafts remain the product-copy source of truth: [Privacy Policy draft](PRIVACY_POLICY_DRAFT.md), [Terms of Use draft](TERMS_OF_USE_DRAFT.md), [Support draft](SUPPORT_DRAFT.md), [metadata behavior](METADATA_REMOVAL.md), and [watermark behavior](WATERMARKS.md). `LegalSite/` is the static presentation of those facts, with visible blockers for every owner/legal fact that is not known.

## Current release boundary

The inspected source has `VeilPublicLinks.privacyPolicy`, `.terms`, and `.support` set to `nil`; no Supabase URL/key is configured. Production purchase and cloud sync are therefore not available in this build. Local editing, system-picker import, export, protected local gallery, metadata Keep/Remove and watermarks work without a Veil account.

Do not turn that current configuration into an unconditional promise that data never leaves the iPhone. Users can explicitly Share or save to Photos; a future configured version may offer consent-based cloud sync. If that deployment is enabled, processed gallery copies and thumbnails plus minimal edit metadata can upload. The new-copy Keep default may carry supported embedded GPS, capture/camera and descriptive fields. Originals and recognized OCR are not uploaded by that sync implementation. The static Privacy page’s cloud section is build-configured and must be reviewed against the actual project region, subprocessors, provider/server logs, backup/tombstone retention, deletion path and cross-border transfers before it is included.

## Owner/legal facts needed before a publishable build

The owner supplies and counsel validates the real controller/developer legal name, public privacy/support contacts, effective date, governing law and consumer-rights language, rights request method, retention and backup periods, service operator/regions/subprocessors/logs, and terms/EULA relationship. If the owner determines the app is a trader for EU distribution, App Store Connect requires verified trader contact information that Apple will display. Keep private values out of Git and provide them locally only during publication preparation. The current `LegalSite/.gitignore` explicitly ignores `/site-config.json` and `/build/`; verify with `git check-ignore -v Documentation/AppStore/LegalSite/site-config.json` before creating a local config. The example config is safe to commit and contains empty values only.

Subscription terms must match actual App Store Connect products. Current approved commercial intent is two successful Save/Share outputs without registration followed by Veil Pro for unlimited protected photo exports; monthly/yearly plans have equal feature access, and the three-day introductory offer applies only when it is configured and Apple confirms eligibility. Exact localized purchase amount and frequency come from the StoreKit product at purchase. The owner reported the monthly product record created; yearly product creation/status is **not verified**. Price, trial, legal-link and production setup are unresolved. Do not publish sales claims until real products, legal links, sandbox/device behavior and cross-device entitlement are complete.

## Static site and publication barrier

- Draft pages: `LegalSite/index.html`, `privacy.html`, `terms.html`, `support.html`, and `site.css`. No JavaScript, analytics, external fonts, embeds, tracking pixels, or external-resource dependencies are used.
- Owner values are read from `LegalSite/site-config.json`, a local file ignored by Git and absent from this change. `site-config.example.json` contains empty values only.
- `python3 Documentation/AppStore/LegalSite/validate.py audit` checks page structure, internal links, copy limits and required disclosure markers without needing owner information.
- `python3 Documentation/AppStore/LegalSite/validate.py build --config Documentation/AppStore/LegalSite/site-config.json --output /tmp/veil-legal-site` is intentionally expected to **fail** until every required field is owner-supplied, legal review is marked complete, trader status is determined, the publication switch is explicitly enabled, and any cloud/commerce sections match the release configuration. A successful command makes a static copy only; it does not deploy or upload anything.
- Placeholder strings and a conspicuous Draft / Not for publication notice remain in the source. The validator refuses to build output if unresolved placeholders or draft markers remain. Keep the generated directory out of source control and publish only after separate owner authorization through their chosen hosting process.

## Candidate binary and dependency inspection — 2026-10-13

The clean Simulator Release and local development-signed arm64 archive both passed test-isolation inspection: no debug photo fixtures/analyzer, local `.storekit`, purchase-testing launch overrides or StoreKitTest linkage. App and Swift Crypto privacy manifests are present. Archive signature verification passed; App Store export/upload validation was not performed. No logging of photos, OCR or custom watermark text was found in the inspected app source. Temporary output is protected and scoped by process/session; current-session shared files can remain until the next launch cleanup. These checks are not a guarantee about receiving apps or OS-managed Photos copies.

Pinned packages remain unchanged: Supabase Swift2.55.3 (Auth), Swift Crypto4.5.2, Swift ASN1 1.7.3, Swift Clocks1.1.1, Concurrency Extras1.4.1, HTTP Types1.8.0 and XCTest Dynamic Overlay1.13.1. Maintainer [Supabase advisories](https://github.com/supabase/supabase-swift/security/advisories) had no published entries when checked. Apple Swift Crypto's [RSA advisory](https://github.com/apple/swift-crypto/security/advisories/GHSA-8q93-f6xh-4f6f) affects3.2.0–4.5.0 and is patched in4.5.1; the [X-Wing advisory](https://github.com/apple/swift-crypto/security/advisories/GHSA-9m44-rr2w-ppp7) affects4.0.0–4.3.0 and is patched in4.3.1. Resolved4.5.2 is outside both affected ranges. This is a bounded published-advisory check, not certification that dependencies have no vulnerabilities.

Apple's [SDK requirements](https://developer.apple.com/support/third-party-SDK-requirements/) include BoringSSL/OpenSSL; Swift Crypto's source dependency contains its namespaced BoringSSL implementation and ships the inspected Crypto privacy resource. No GoogleSignIn binary SDK is integrated: the existing Google provider path uses native web authentication when configured. Source-package builds do not substitute for reviewing the final archive's aggregate privacy report and current SDK requirements. Source API scan found no required-reason UserDefaults/file-timestamp/disk-space/boot-time access in the app and linked Auth/Helpers paths. Reconcile the manifest's conservative optional-account/cloud data entries with the actual release scope before App Privacy submission.
